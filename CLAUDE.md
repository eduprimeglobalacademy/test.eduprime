# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

EduPrime — white-label, multi-tenant React + Vite + Supabase MCQ/assessment platform. Each customer is an `organizations` row with its own subdomain and branding. Four roles:
- **Platform Super Admin** — EduPrime staff, cross-org, not tied to any `organizations` row (`platform_admins` table). No self-serve path to becoming one — bootstrapped by hand after the auth user already exists (see Environment below). Deliberately does *not* get access to any org's `test_attempts`/`student_answers`/`questions` — billing/support scope, not a standing grant to end-user data.
- **Org Admin** — manages educator access tokens, revokes accounts, scoped to one org (`admin_users` table — the name predates multi-tenancy)
- **Teacher/Educator** — creates and manages tests/assessments, scoped to one org
- **Student** — takes assessments via code-based join flow (no login), scoped to one org via the test they join

Originally built in Bolt as a single-tenant app, migrated to Replit, then converted to multi-tenant (see `supabase/migrations/20260810120000_platform_organizations.sql` for the tenancy migration). Supabase accessed directly from the frontend — no Express/custom backend. Two Edge Functions: `validate-teacher-token` (consumes a teacher_tokens row, creates the auth user + `teachers` row) and `create-organization` (self-serve org signup — creates the `organizations` row, the admin's auth user, and the `admin_users` row together). Both need elevated (service-role) privileges the anon key doesn't have.

## Architecture

**Tenant resolution**: `src/lib/tenant.ts`'s `resolveSlugFromHostname()` maps `window.location.hostname` to an org slug for the `orgname.eduprime.app` form; `isPlatformRootHost()` separately identifies hosts that are never a tenant (bare root domain, `localhost`, `*.vercel.app`) — the two are deliberately not the same check, since a hostname can fail the subdomain match *and* not be a platform host, meaning it might be a custom domain (see Custom domains below). `src/contexts/TenantContext.tsx` wraps the whole app, resolves the org against the `organizations` table (by slug, or by `custom_domain` when there's no slug match and it's not a platform host), and exposes `useTenant()` (`org`, `loading`, `notFound`, `isRootDomain`, `refetchOrg`). It also pushes `org.primary_color`/`secondary_color` onto `document.documentElement` as `--brand-primary`/`--brand-secondary` — that's the entire theming mechanism, see Styling below. Root-domain visitors see `RootMarketing` with a self-serve org signup (`CreateOrganizationModal` → `create-organization` Edge Function); unresolvable subdomains see `OrgNotFound`.

**Google sign-in ("SSO")**: chose Google OAuth over generic SAML — the realistic customer here is a school/coaching institute already on Google Workspace, not an enterprise with a SAML IdP to configure, and SAML would need Supabase's paid Enterprise SSO add-on plus per-customer metadata exchange for a need this audience mostly doesn't have. Built as **link-while-authenticated**, not cold sign-up: `connectGoogleAccount()` (`ConnectGoogleButton`, shown in `AdminDashboard`/`TeacherDashboard` headers) calls `supabase.auth.linkIdentity()` from an already-signed-in session, attaching Google to that exact `auth.users` row — only after that does `signInWithGoogle()` (the "Continue with Google" button on `SignInModal`) work for that account. Deliberately not the other way around (cold `signInWithOAuth` auto-creating/matching an account by bare email) — that shape is a known account-linking risk, and here it would also bypass the token/`create-organization`-gated invite model every other account creation path goes through. A cold Google sign-in for an unlinked email fails safe: either Supabase rejects it or it lands on an auth user with no `admin_users`/`teachers` row, so `getCurrentUser()` returns null either way — same "user not found" as any other unrecognized account, not a security gap. Requires the Google provider enabled in the Supabase Auth dashboard (OAuth client id/secret from Google Cloud Console, redirect URL allowlisted) — not something this repo can configure, same category of manual prerequisite as the Razorpay/Vercel setup.

**Isolated-DB tier — deliberately not built**: considered and rejected for now, not an oversight. It would mean provisioning a separate Supabase project per top-tier customer, which breaks the single-shared-client assumption `src/lib/supabase.ts` and every migration in this repo is built on — a real architecture fork (dynamic per-tenant connection routing or per-tenant deployments), not a feature flag. With zero live orgs today, building that speculatively is exactly the premature-engineering trap worth avoiding. If it's ever needed: it'd be a separate Supabase project + either a second deployment or a connection router keyed off `organizations.custom_domain`/`slug`, migrations replayed per project, and it only makes sense to build once a specific Institution customer is actually asking for it.

**Custom domains**: `organizations.custom_domain`/`custom_domain_status` ('pending' | 'active'). Org admin sets the domain itself (`CustomDomainCard` in `BillingPanel`, gated to Growth/Institution plans in the UI, not at the RLS layer — there's no real security stake in who flips this specific status field, see the migration's comment for why). A DB trigger resets status to 'pending' whenever the domain value changes, so editing it always requires re-activation. Activation itself (`SuperAdminConsole`'s domain column, click the pending/live pill to toggle) is a platform-admin action — but it's a communication step, not the thing that actually makes the domain work: this app never talks to Vercel's API (no token in this environment), so someone still has to add the domain in the Vercel project dashboard by hand and the customer still has to point DNS at `cname.vercel-dns.com` before any request ever reaches this app on that hostname.

**Routing**: still no router library. `App.tsx` manually switches on `user.role` (from `AuthContext`), tenant state (from `TenantContext`), and `window.location.pathname` to pick between `RootMarketing`, `LandingPage`, `AdminDashboard`, `TeacherDashboard`, or `TestAccess`. `/test` and `/assessment` paths force the student test-access view on any host (including the root domain, so pre-tenancy links keep working), and there `TestAccess`/`TestInterface` filter the test lookup by `org_id` whenever a tenant is resolved.

**Auth**: `src/contexts/AuthContext.tsx` wraps the app and exposes `useAuth()` (`user`, `loading`, `refreshUser`), and subscribes to `supabase.auth.onAuthStateChange` (not just a mount-time check) specifically so an OAuth redirect-back reliably lands — the SPA reloads on that redirect, and relying on mount-time `refreshUser()` alone risks a race against supabase-js parsing the token out of the URL. `src/lib/auth.ts` has `signInWithEmail` / `signUpTeacher`. Roles (`admin` | `teacher`) come from Supabase Auth + the `teachers`/admin lookup, not a separate role table on the client. Auth is not currently scoped to the subdomain it's used on — a Supabase session works from any host — so signing in only makes sense on the org's own subdomain even though nothing technically blocks it elsewhere; the UI only offers sign-in from within `LandingPage` (per-org), not from `RootMarketing`. Students never authenticate — they join via a test code, so student flows don't use `AuthContext`.

**Data layer**: `src/lib/supabase.ts` is the single Supabase client instance plus every shared TypeScript interface (`Organization`, `Test`, `Question`, `QuestionOption`, `TestAttempt`, `StudentAnswer`, `TeacherToken`, etc.) — check here first before adding new types. Components query Supabase directly (no repository/service layer). `org_id` lives on `admin_users`, `teachers`, `teacher_tokens`, `tests`, and `test_attempts`; DB triggers (`set_teacher_org_id`, `set_test_org_id`, `set_attempt_org_id`) auto-derive it server-side from the token/teacher/test being referenced, so insert payloads from the client never need to (and can't be trusted to) supply it themselves.

**Org signup flow**: `RootMarketing` → `CreateOrganizationModal` → `create-organization` Edge Function creates the `organizations` row (14-day trial), the admin's auth user, and the `admin_users` row, then the browser is redirected to `https://{slug}.{VITE_ROOT_DOMAIN}`.

**Educator onboarding flow**: Org Admin generates a token (`teacher_tokens` table, org-scoped) → educator registers via `RegisterModal` using the token → `validate-teacher-token` Edge Function checks/consumes it → row created in `teachers` (org_id derived from the token via trigger).

**Test lifecycle**: `CreateTestWizard` (3 steps: info → settings → grading, incl. A/B/C/D/F grade boundaries) → questions added/bulk-imported via `CreateQuestionPage` → test set to `draft`/`live`/`closed` (`TestStatus`) → student joins with `test_code` in `TestAccess` → `TestInterface` (timer, per-question or overall, auto-submit on expiry, optional back-navigation; duplicate-attempt check goes through the `has_attempted` RPC rather than a direct table read) → answers written to `student_answers` → `TestResults` shows score/grade + PDF export (jspdf), rendered entirely from the just-created attempt object, no re-fetch → teacher views aggregate analytics + CSV export in `TestReports` (Recharts pie/bar).

**Plan limits (hard-enforced)**: `plans` table (`starter`/`growth`/`institution`, `NULL` on any limit column means unlimited) joined via `organizations.plan_id`. `src/hooks/usePlanLimits.ts` reads the current org's plan; `src/components/ui/UsageMeter.tsx` renders a used/limit bar and switches to a warning message at/over the limit — but this is no longer purely visual. Three `SECURITY DEFINER` functions (`org_within_teacher_limit`, `org_within_active_test_limit`, `org_within_test_student_limit` — added `20260812060000`–`20260813030000`, after the `growth`-trial-by-default decision below was written) gate `FOR INSERT` RLS policies on `teacher_tokens`, `tests`, and `test_attempts` respectively, blending in any active `org_capacity_addons` quantity on top of the plan's base limit. A `BEFORE UPDATE` trigger (`enforce_test_reactivation_limit`) closes the gap `INSERT`-only enforcement would leave on reactivating a `closed` test back to `draft`/`live`. Client-side, `AdminDashboard`'s token form and `TestAuthoring`'s `handleSaveSettings` pre-check the same limit (using the plan + addon totals) before attempting the insert, so the UI usually shows an upgrade prompt before the DB ever has to reject anything; the RLS policy is the real backstop and also surfaces as Postgres error code `42501` on the rare race, caught specifically to show a capacity/billing message instead of a raw DB error (`TestList.tsx` catches the same code on the reactivation-trigger path). New orgs default to `growth` regardless of what they'll eventually pay for, since the 14-day trial is meant to be full-featured.

**Billing (Razorpay, hard-enforced)**: `subscriptions` table (one row per org's Razorpay subscription, service-role-write-only) plus `organizations.grace_ends_at`/`razorpay_customer_id` and `plans.razorpay_plan_id`/`price_inr`. `BillingPanel` (inside `AdminDashboard`, toggled via a header button) calls the `razorpay-create-subscription` Edge Function to get a subscription id, then `src/lib/razorpay.ts` opens Razorpay Checkout against it. `razorpay-webhook` (HMAC-verified against `X-Razorpay-Signature`, no Supabase auth — Razorpay calls it directly) is the only writer of subscription/org status: `subscription.activated`/`charged` → org `active`; `subscription.pending` → org `past_due` with `grace_ends_at` set 7 days out (only on the *first* pending webhook, so repeated retries don't keep resetting the clock); `subscription.halted` → `suspended`; `subscription.cancelled` → `cancelled`. The DB function `org_can_write(org_id)` (trial/active, or past_due-but-still-inside-grace) gates the *creation* of new tests and new teacher_tokens via dedicated `FOR INSERT` policies — reading, editing, or deleting what already exists (including closing a live test or revoking a token) deliberately stays ungated, so a lapsed org can still wind itself down and students mid-exam are never blocked. `validate-teacher-token` re-checks `org_can_write` explicitly via RPC since it runs as service_role and bypasses RLS. `OrgStatusBanner` (`src/components/billing/`) surfaces trial/past_due/suspended state in both `AdminDashboard` and `TeacherDashboard`; `CreateTestWizard`/`AdminDashboard`'s token form catch Postgres error code `42501` (RLS violation) specifically to show a billing-specific message instead of a raw DB error.

**Classes / course sections**: `classes` (org- and teacher-scoped: `name` e.g. "Section A", plus free-text `course_name`, `grade_level`, `academic_term` — the four axes SIS/LMS platforms typically separate, kept as plain text rather than normalized lookup tables since nothing yet needs to report *across* orgs by grade or term). `tests.class_id` is nullable — a test isn't required to belong to a class, for one-off assessments. `src/hooks/useClasses.ts` (fetch + create, scoped to one teacher) backs two independent entry points: `ClassPicker` (dropdown with inline "create new class", used inside `TestAuthoring`/`EditTestModal` when assigning a test to a class) and the standalone class-management flow reached via the sidebar's "Classes" nav — `ClassGrid` (list + create, one card per class with live-test/assessment-count badges) → `ClassDetail` (per-class stats + its assessments) → `ClassSettings` (edit properties, delete class, roster: enrollment link/QR code, add/remove students). Screens that show a test's class embed it via `.select('*, classes(...))` (`TeacherDashboard`, `TestReports`) rather than a separate query — `Test.classes` on the shared type is only populated when a caller does that embed, plain `.select('*')` leaves it `undefined`.

**Platform Super Admin console**: `SuperAdminConsole` (`src/components/superadmin/`) — org directory (status, plan, teacher/test counts, next renewal), MRR (sum of active orgs' plan price — trial orgs excluded since they're unpaid), plan reassignment, and suspend/reactivate. `App.tsx` checks `user.role === 'platform_admin'` *before* tenant resolution matters (`notFound`/`isRootDomain`/etc.) — platform staff aren't scoped to a subdomain, so the console has to be reachable from any host, including a mistyped one. They sign in through the same `SignInModal` every other role uses (auth is global, not subdomain-scoped — see Auth above); `RootMarketing` has a small "EduPrime team sign in" link since platform staff have no org subdomain of their own to sign in from.

**Impersonation ("view as")**: cross-app handoff, initiated from the standalone `eduprime-admin` console, not from this repo. `Organizations.tsx`'s "View as" modal lets a platform admin pick the org's Admin account or any specific teacher in that org (a `<select>` populated from `teachers` for that org_id) before calling `src/lib/auth.ts`'s `impersonate(orgSlug, orgId, teacherId?)`, which POSTs to this repo's `impersonate-org` Edge Function. The function verifies the caller is a `platform_admins` row, resolves the target (a `teacherId` is checked against `org_id` so it can't cross orgs; omitted means the org's admin), and mints a session via `auth.admin.generateLink({type:'magiclink'})` immediately redeemed server-side with `verifyOtp` — no email is sent, no password is ever touched or reset. Every impersonation is logged to `impersonation_log` (append-only, `service_role`-insert-only from inside the Edge Function) before the tokens are returned to the console, which opens a new tab at this app's URL with the tokens carried in the hash fragment (`buildSessionHandoffUrl`/`consumeSessionHandoff` in `src/lib/auth.ts` — hash only, never a query string, stripped from the visible URL immediately on consumption either way). A persistent amber `ImpersonationBanner` (state from `getImpersonationState()`, reading the `sessionStorage` stash `consumeSessionHandoff` writes) is mounted at the top of `App()`, outside the role-based view switch, so it's visible regardless of which screen renders under it; `exitImpersonation()` clears the stash. Known limitation, accepted deliberately rather than solved: the impersonated session lands on whatever host it's opened on (typically the root domain, since the console doesn't know the org's subdomain ahead of the handoff), not the target org's own subdomain — RLS still scopes all data correctly (it keys off the authenticated `admin_users`/`teachers` row, not the hostname), but the org's own branding won't show during the session, just EduPrime's default look.

**Supabase schema** (see `supabase/migrations/`): `organizations`, `plans`, `subscriptions`, `classes`, `platform_admins`, `impersonation_log`, `teacher_tokens`, `teachers`, `tests`, `questions`, `question_options` (one option per question flagged `is_correct`), `test_attempts`, `student_answers`. Row-level security is the *only* authorization layer (Supabase is queried straight from the browser) — every admin-facing policy is scoped to the caller's own org via the `is_admin()` / `auth_admin_org_id()` / `auth_teacher_org_id()` SQL helper functions (SECURITY DEFINER, defined in the tenancy migration) rather than duplicating the org-lookup subquery per policy. Check the migrations before changing query patterns or adding a table that needs tenant isolation.

**Styling**: Tailwind CSS. Brand color is runtime-themeable via two CSS custom properties set in `src/index.css`'s `:root` (`--brand-primary`, `--brand-secondary`, defaulting to EduPrime's own Indigo/Violet) and overridden per-org by `TenantContext`; hover/active shades are derived with `color-mix()` rather than stored separately. Design-system utility classes (`.gradient-text`, `.btn-primary`, `.btn-outline`, `.input-base`, `.stat-card`, `.page-header`, `.badge`, `.card-glass`, `.animate-in`, `.scrollbar-thin`) and the `Button`/`Input` primitives in `src/components/ui/` read from those variables. Every screen (including teacher/admin dashboards, not just the public-facing surfaces) now reads brand color from the CSS variables — no hardcoded `indigo-*`/`violet-*` Tailwind classes remain anywhere in `src/`. Cards are `rounded-2xl`, inputs/buttons `rounded-xl`.

**Reusable UI primitives**: `src/components/ui/` — `Button` (variants: primary, outline, ghost, danger, secondary), `Card`, `Input` (labeled, with error/helper text), `LoadingSpinner`.

## Environment

Required env vars (`.env`, not committed): `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_SUPABASE_SERVICE_ROLE_KEY` (service role key is used for admin-only operations — treat as sensitive, don't expose in client code paths a student can reach), `VITE_ROOT_DOMAIN` (e.g. `eduprime.app`; defaults to `eduprime.app` if unset — used to strip the org slug off the hostname and to build the redirect URL after org signup).

Bootstrapping the first Platform Super Admin (no UI for this on purpose): create the person's auth user (dashboard or `supabase.auth.signUp`), then `INSERT INTO platform_admins (user_id, email, name) VALUES ('<their auth uid>', '<email>', '<name>');` directly via SQL.

Edge Function secrets (set via `supabase secrets set`, not `.env` — these run server-side only): `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` (used by `razorpay-create-subscription`), `RAZORPAY_WEBHOOK_SECRET` (used by `razorpay-webhook` to verify `X-Razorpay-Signature`; set to the same secret configured on the webhook in the Razorpay dashboard). None of these are `VITE_`-prefixed on purpose — the key *secret* must never reach the browser bundle. The Checkout.js frontend flow only ever sees `RAZORPAY_KEY_ID`, returned by `razorpay-create-subscription` at call time, not baked into the client build.
